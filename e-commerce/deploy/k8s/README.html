E-commerce platform README.md

Kubernetes overlays#

The whole e-commerce system on Kubernetes, for three environments, built with Kustomize from each service's own k8s/ base. Data stores are custom resources of their operators. Design: design/03-deployment.md.

cd e-commerce/deploy/k8s
./verify.sh                                   # build dev, staging and prod
./verify.sh --server                          # and dry-run every object on a kind cluster against the operators' CRDs
kubectl apply --server-side -k overlays/dev   # deploy (operators installed first, below)

Layout#

base/
  namespaces.yaml        e-commerce-shop (services, edge, analytics) and e-commerce-platform (data stores, Kafka, Keycloak)
  shop/                  the 11 service bases + NGINX edge, unchanged; default deny; aliases to the platform stores;
                         in-cluster JWK set URIs; RuntimeDefault seccomp; the edge certificate; KEDA credentials
  platform/              PostgreSQL + PgBouncer, Kafka + topics, Redis, OpenSearch, Cassandra, RabbitMQ, Keycloak + realm;
                         backups.yaml: WAL archive and nightly backups of every PostgreSQL cluster (30 days)
components/
  hosts/                 copies an overlay's host names (its environment.yaml) into issuers, CORS, realm, certificates
  single-replica/        dev sizing: one of everything, replication factor 1
  dev-secrets/           fixed dev passwords
  external-secrets/      secrets from the environment's vault (staging, prod)
  local-mail/            Mailpit (dev, staging)
  local-object-storage/  RustFS as the S3 store (dev, staging)
  self-signed-tls/       self-signed ClusterIssuer (dev)
  test-users/            ada, bob (customers) and sam (staff), and the password grant (dev)
  signed-images/         Kyverno policy: only images signed by the CI image workflow on main, with a signed SBOM (staging, prod)
  encrypted-storage/     every data store's volumes on the encrypted StorageClass "encrypted-ssd" (staging, prod)
overlays/
  dev/  staging/  prod/

Where things run#

  • e-commerce-shop: every service, the NGINX edge (the only LoadBalancer) and the analytics ClickHouse. Default deny; each workload's own policy (in its service base) opens what it needs. Short store names in the service settings (kafka-bootstrap, pgbouncer-orders, redis-cart, …) are ExternalName aliases to the platform namespace, so the bases stay the same as in the local stack.
  • e-commerce-platform: one CloudNativePG cluster per owning service (orders, inventory, payments, catalog) and one for Keycloak; PgBouncer poolers in transaction mode for orders, inventory, payments and catalog; Kafka in KRaft mode with the topics of the event catalogue; Redis per use (redis-cache, redis-ratelimit, redis-cart, redis-reco, redis-notify); OpenSearch; Cassandra (data centre dc1); RabbitMQ with notification's own user; Keycloak with the shop realm. Ingress is allowed from this namespace, the shop namespace, the operators, monitoring and ingress-nginx.

redis-notify is separate from the cache on purpose: an LRU eviction of a sent-log entry would let an email go out twice.

verify.sh --server checks every manifest against exactly these CRD versions.

Cluster-level objects the staging and prod overlays expect:

  • ClusterIssuer letsencrypt-staging (staging) and letsencrypt (prod), with the DNS-01 solver of the zone's DNS provider.
  • ClusterSecretStore e-commerce, pointing at that environment's vault, holding these keys:
Key Properties Becomes
e-commerce/orders-db, inventory-db, payments-db, catalog-db, keycloak-db username, password database owner secrets in both namespaces
e-commerce/notification-rabbitmq username, password the RabbitMQ user and notification's RABBITMQ_URL
e-commerce/object-storage access_key, secret_key catalog's S3_ACCESS_KEY, S3_SECRET_KEY
e-commerce/analytics default_password, grafana_password ClickHouse passwords
e-commerce/storefront client_secret, session_keys the storefront's realm client secret (also in Keycloak's realm import) and its session encryption keys
e-commerce/order-service-oidc, cart-service-oidc client_secret the service's realm client secret, in both namespaces: Keycloak's realm import and the service read the same value (ADR 0014)
e-commerce/backup-storage access_key, secret_key the database backups' key: write access to the e-commerce-backups bucket only
  • An egress-gateway namespace (payment provider, object storage) and an ingress controller in ingress-nginx in front of Keycloak.
  • Nodes with vm.max_map_count=262144 for OpenSearch (the operator's privileged init container is off).
  • Staging and production: a StorageClass encrypted-ssd whose volumes are encrypted at rest with a customer-managed key (for example the provider's CSI driver with a KMS key), and an e-commerce-backups bucket with versioning and an object lock or retention rule, so a compromised cluster cannot delete its own backups. In dev the backup bucket is created in RustFS by a Job.

Using dev#

kubectl -n e-commerce-shop port-forward svc/edge 8443:443           # the shop API through the edge
kubectl -n e-commerce-platform port-forward svc/mailpit 8025        # emails
kubectl -n e-commerce-platform port-forward svc/minio 9000          # browser uploads (presigned URLs point here)

Tokens come from https://id.dev.shop.example/realms/shop with the test users (ada / ada, sam / sam), as in the local stack's smoke test.

Known gaps#

Edge NGINX and ClickHouse run as root (warned against restricted, allowed by baseline) Both drop to an unprivileged worker or user inside the image Unprivileged NGINX image; ClickHouse with runAsUser: 101
